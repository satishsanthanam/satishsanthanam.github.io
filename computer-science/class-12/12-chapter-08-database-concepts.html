Computer Science: Class 12 — Chapter 8: Database Concepts

8.1 Introduction to Data Management

Data management is critical for storing and retrieving information efficiently. Manual record keeping, such as using paper registers, becomes tedious and error-prone as data volume grows.

Limitations of Manual Record Keeping
  • Repetitive Data Entry: Re-entering student details (Roll number, name) upon promotion or on monthly attendance sheets.
  • Inconsistency: High risk of spelling errors, mismatched names, or skipped records.
  • Data Loss: Physical damage or loss of registers.
  • Calculation Errors: Manual consolidation of attendance percentages is prone to mistakes.
8.2 File System & Its Limitations

A file system stores data in separate files on a computer's storage device. While files can be accessed and searched, retrieving complex data requires custom application programs.

Key Limitations of File Systems
  • Difficulty in Access: Files do not provide built-in query mechanisms; developers must write custom application programs to retrieve data in specific formats.
  • Data Redundancy: Duplication of identical data across multiple files (e.g., student names stored in both student and attendance files), leading to wasted storage.
  • Data Inconsistency: Occurs when redundant data is updated in one file but not in another, leading to conflicting records.
  • Data Isolation: Files are created in isolation, often in different formats, with no logical mapping or links between them.
  • Data Dependence: The structure of the data file is tightly coupled with the application programs; changing the file format requires modifying all accessing programs.
  • Controlled Data Sharing: Difficulty in enforcing granular security and access permissions (e.g., allowing teachers to edit attendance while restricting parents to read-only access).
8.3 Database Management System (DBMS)

A Database Management System (DBMS) is software designed to create, manage, and retrieve logically related data efficiently, overcoming the limitations of file systems.

Technical Profile: Database Management System (DBMS)

  • Architecture Layer / Tier: Software interface layer between physical storage files and end-user applications.
  • Operational Mechanics & Syntax: Uses structured query languages (SQL) to perform CRUD (Create, Read, Update, Delete) operations, enforcing schema definitions and constraints.
  • System Trade-offs & Failures: High initial cost of hardware/software, training overhead, and increased vulnerability due to centralized data storage (single point of failure).
Key Concepts in DBMS
  • Database Schema: The logical design or skeleton of the database, defining tables, columns, data types, constraints, and relationships.
  • Data Constraint: Restrictions on data values (e.g., NOT NULL , UNIQUE ) to ensure accuracy and reliability.
  • Meta-data / Data Dictionary: Data about data (schema definitions, constraints) stored in the database catalog.
  • Database Instance: The actual snapshot of the database state at any given point in time.
  • Query: A formal request to retrieve specific information from the database.
  • Data Manipulation: Operations to modify the database, including Insertion, Deletion, and Update.
  • Database Engine: The core software component that processes queries and manages physical storage.
8.4 Relational Data Model

The Relational Data Model organizes data into tables, known as relations . It is the most widely used data model in modern database systems.

Relational Terminologies
  • Attribute: A column in a relation representing a specific property or characteristic (e.g., SName ).
  • Tuple: A row in a relation representing a single record of an entity.
  • Domain: The set of all permissible values for an attribute (defined by data types).
  • Degree: The total number of attributes (columns) in a relation.
  • Cardinality: The total number of tuples (rows) in a relation.
Properties of a Relation
  • Each attribute has a unique name, and their order is immaterial.
  • Each tuple is distinct (no duplicate rows), and their order is immaterial.
  • All values under an attribute must belong to the same domain.
  • Each attribute value must be atomic (indivisible).
  • No attribute can have multiple values in a single tuple.
  • The special value NULL is used to represent missing or unknown data.
8.5 Keys in a Relational Database

Keys are attributes or sets of attributes used to uniquely identify tuples within a relation and establish relationships between tables.

Technical Profile: Relational Database Keys

  • Architecture Layer / Tier: Logical schema design and integrity enforcement layer.
  • Operational Mechanics & Syntax: Primary keys enforce entity integrity (uniqueness, non-null); Foreign keys enforce referential integrity by linking referencing and referenced relations.
  • System Trade-offs & Failures: Over-indexing or complex composite keys can degrade write performance; improper foreign key cascading can lead to accidental data deletion or update anomalies.
Types of Keys
  • Candidate Key: Any attribute or minimal set of attributes that can uniquely identify every tuple in a relation.
  • Primary Key: The specific candidate key selected by the database designer to uniquely identify tuples. It cannot contain NULL values.
  • Composite Primary Key: A primary key composed of two or more attributes when no single attribute can guarantee uniqueness (e.g., {RollNumber, AttendanceDate} ).
  • Foreign Key: An attribute in a referencing relation whose values must match the primary key of a referenced relation, enforcing referential integrity.

Case Study: Transitioning a School Attendance System from Files to a Relational Database

Socio-Technical Analysis & Core Systemic Impact: In a manual or file-based system, student and guardian details are duplicated across multiple files, leading to data redundancy and inconsistency. By decomposing the flat files into three normalized relations— STUDENT , GUARDIAN , and ATTENDANCE —and establishing relationships via GUID (Foreign Key) and RollNumber , the system ensures data integrity. Any update to a guardian's phone number is made exactly once in the GUARDIAN table, instantly reflecting across all related student records without risk of inconsistency.
